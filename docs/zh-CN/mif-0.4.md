## 前言

本工作草案旨在支持磨坊棋实现者、数据库作者、研究项目、
锦标赛工具开发者和规则历史学家之间的讨论。

本文档中使用的动词形式遵循标准编写规范：
`shall` 表示要求；`should` 表示推荐；`may`
表示允许；且 `can` 表示可能性或能力。

附录 A 至 D 是规范性的。附录 E 和 F 是资料性的。

## 引言

现有软件通常将几种不同的表示形式称为“FEN”：
一个用户可复制的局面、一个引擎快照、一个置换键以及一个已保存的
比赛。这些对象并不具有相同的等价关系。

因此，本草案将以下内容进行了区分：

- **MFEN**，在调用方提供的规则集上下文下的精确瞬时状态，包括未解决的吃子；
- **MPK**，由配置文件声明的、对称归一化的结构分析键；
- **MSTATE**，包含事件、重复观察和和棋声明历史的可恢复 JSON 游戏状态；以及
- **MRS**，一种规范的 JSON 规则集清单，用于选择其转换在本文档中定义的有限机制。

这种分离是刻意为之的。MPK 不是无损的保存文件。MFEN 不会虚构缺失的历史。MSTATE 不会在主动作中隐藏补充吃子。

MFEN 刻意不把规则集身份写进紧凑的局面行。因此，若要按语义使用
MFEN，调用方必须提供完整且带版本的规则集身份并解析其清单；非正式
名称或单字母标签不是规则集身份。

公开的点位顺序也与引擎的内部节点编号相分离。符合性的引擎可保留任何紧凑型棋盘或位棋盘布局，并仅在交换边界处执行 24 项置换。

# 1 范围

本文档规定：

a) 用于 24 点位磨坊棋盘的公开坐标、点位、线路和变换模型；

b) MFEN/0.4，在调用方提供的规则集上下文下的瞬时状态的规范文本表示；

c) MPK/0.4，在显式键配置文件下用于结构分析的规范文本键；

d) MSTATE/0.4，一种关于起点、事件序列、一个
当前检查点、重复观察和声明的 I-JSON 表示；

e) MRS/0.4，一种用于选择本版中定义的有限规则
机制的规范规则集清单；以及

f) 解析、验证、规范化、错误和符合性要求。

本版涵盖附录 A 的 24 个点位上的两种拓扑：

- 标准九子棋拓扑：16 条正交成磨线；或
- 对角线变体拓扑：另加 4 条对角成磨线，共 20 条。

A.2 的快速示意图直观显示了二者差异；注册的拓扑标识符仍为权威定义。

本文档不：

- 声明某个命名的社区或联合会使用特定的规则集；
- 标准化锦标赛管理、时钟、等级分或配对；
- 要求引擎在内部使用公开的点位顺序；
- 标准化内存中或二进制数据库的布局；
- 使 MPK 足以用于等效性取决于所选键配置文件中省略的状态
  的数据集；或
- 允许通过组合未注册的布尔开关来描述任意
  规则。

# 3 术语和定义

就本文件而言，适用以下术语和定义。

## 3.1 行动方

被要求执行下一个游戏动作的玩家

## 3.2 权威状态

由于未来的合法行为或精确恢复能够依赖于该值而对其进行序列化

## 3.3 规范形式

给定符合性数据模型的单一允许序列化形式

## 3.4 选择分支

备选方案中一个完整的义务序列，其中选择第一个目标即意味着承诺该序列并舍弃其他序列

## 3.5 延迟移除标记

针对已移除棋子的、保留所有者的棋盘标记，其可见标记在达到规则定义的清除边界前保持阻塞状态

## 3.6 派生值

能够从权威状态和识别出的规则集中唯一地重新计算出的值

## 3.7 扩展字段

固定 MFEN 或 MPK 核心之外的命名字段

## 3.8 键配置文件

MPK 投影、转换集和规范比较的版本化定义

## 3.9 活动棋子

在移动、磨坊、吃子和物料规则中占据一个点位的棋子

## 3.10 逻辑回合

一个主动作，以及在下一个主动作前必须解决的零个、一个或多个后续
补充移除

注 1：一个逻辑回合可以跨越多个序列化状态。主动作产生义务时，该义务
作为权威未决状态保留，直到所选分支中的全部移除完成且 11.20 的确定性
稳定边界处理结束。

## 3.11 义务

要求指定的参与者因指定原因从指定区域移除一个或多个目标的权威性要求

注 1：在普通九子棋中，成磨会产生强制的吃子/移除义务。义务是待履行
的要求；移除是履行该要求并改变状态的操作。

## 3.12 主动作

增加 `primary-ply` 的落子或移动

## 3.13 规则集

由 MRS 清单识别的版本化游戏语义

## 3.14 稳定局面

没有未决义务的进行中局面

## 3.15 状态配置文件

位置数据模型及其文本编码的版本化定义

## 3.16 补充动作

为解决吃子/移除义务而执行的移除，且不计为主动作

注 1：本文以 *capture（吃子）* 表示规则机制或权利，以
*removal（移除）* 表示实际改变棋盘或手中状态的操作；不会把其中一个
词全局替换为另一个。

# 4 符合性

## 4.1 符合性类别

一个实现可声明以下一个或多个类别：

- MFEN 生产者；
- MFEN 消费者；
- MPK 生产者；
- MPK 消费者；
- MSTATE 生产者；
- MSTATE 重放器；
- MRS 生产者；
- MRS 解析器；
- MIF 转换器；以及
- 转换配置文件实现。

符合性声明应列出每一个受支持的格式签名、状态配置文件、语义配置文件、拓扑结构和键配置文件。

`MIF 转换器`声明还应列出 12.4 下支持的源映射、目标格式和转换状态。

## 4.2 生产者

符合性的生产者应：

a) 发出本文件指定的规范形式；

b) 发出状态和规则集要求的每一个权威字段；

c) 不得使用派生估计值来替代缺失的权威状态；

d) 不得发出其未实现的语义的标识符；并且

e) 满足附录 D 中所有适用的规范语料向量。

## 4.3 消费者和重放器

符合性的消费者或重放器应：

a) 在语义处理前验证语法；

b) 解析并验证状态配置文件、调用方提供的或封装的规则集清单，以及在适用时的键配置文件；

c) 拒绝不一致的权威字段，而不是静默地修复它们；

d) 将结构有效性与从标准初始局面出发的可达性区分开来；

e) 按第 13 条的要求，保留已知的私有非语义扩展；并且

f) 满足所有适用的规范语料向量。

## 4.4 结构有效性与可达性

一个 MFEN 能够是结构有效的，但可能无法从一个命名的初始局面到达。消费者可提供可达性检查，但其应将 `unreachable` 与语法、配置文件解析和状态一致性分开报告。

## 4.5 往返

对于每一个受支持的有效输入，解析后的规范序列化应产生预期的规范输出，且不丢失权威状态。

对于 MSTATE，对 `origin` 加上 `events` 的重放应完全按照第 9 条的规定产生 `current`、`repetitionHistory` 和 `claims`。

# 5 通用约定与配置文件模型

## 5.1 字符集与大小写

MFEN 和 MPK 应仅包含 US-ASCII。Token 对大小写敏感。

MSTATE 和 MRS 应为 UTF-8 I-JSON。不得输出字节顺序标记。

## 5.2 空白符

MFEN 和 MPK 在字段之间应仅使用一个 U+0020 空格。空白符
不得出现在字段内部。前导和尾随空白符不属于记录的一部分，且不得输出。

传输帧（包括最后的 CRLF）位于记录语法之外。

## 5.3 整数

文本整数应使用不带前导零的无符号十进制表示法，但零应为 `0`。

MFEN、MPK、MSTATE 和 MRS 中的每个精确整数都应处于以下闭区间范围内：

```text
0 .. 9007199254740991
```

生产者不得将该范围之外的整数编码为 JSON 数字。需要更大精确值的版本应定义一个十进制字符串成员。

## 5.4 玩家

`w` 代表白方，即第一位玩家。`b` 代表黑方，即第二位
玩家。颜色名称并不意味着物理棋子的颜色。

## 5.5 坐标与位集

坐标和公共点位顺序应如附录 A 所规定。

24 点位位集应为六位小写十六进制数字。位 `i` 应
指向公共点位索引 `i`；第 0 位是该数值型十六进制值的最低有效位。应包含前导零。

线路位集应使用表 A.2 中的线路 ID。对于 16 线路拓扑，应为四位小写
十六进制数字；对于 20 线路拓扑，则应为五位。未使用的位应为零。

## 5.6 标识符

标识符应符合附录 C，且长度不得超过 63 个 ASCII
字符。

规则集引用应具有如下形式：

```text
<identifier>@<positive-integer>
```

以 `x-` 开头的标识符是私有的或临时的。本草案的
符合性测试件特意使用了 `x-`；它们并未预留未来的公共
名称，例如 `nmm@1`。

## 5.7 摘要

清单摘要应为：

```text
sha256:<64 lowercase hexadecimal digits>
```

摘要输入应为清单对象本身的 RFC 8785 JCS UTF-8 字节流。包含的 `digest` 成员不得插入到该清单
对象中。

清单摘要是信封或传输元数据。MPK 通过 `id@version` 标识规则集；MFEN 从其调用方
或包含的信封中接收规则集身份和清单。两种文本记录均不重复清单摘要。

## 5.8 权威状态与派生状态

在适用时，以下数值是权威的：

- 棋盘字符，包括延迟移除标记的所有权；
- 行动方、阶段和动作；
- 直接手中棋子数量；
- 义务分支、有序记录、剩余计数和目标集；
- 无进展计数；
- 主步数；
- 终局结果；
- 规则集声明的每个语义扩展；
- MSTATE 中的重复观察和声明记录；以及
- 识别出的规则集清单。

当前盘上活棋子数、空点位计数、当前完整的磨坊线路和
普通移动性是派生的。

历史落子计数通常**不**是派生的。特别是：

```text
placed != initial pieces - current hand
```

当手中棋子可以被吃除时，便会出现上述不等关系。历史落子计数不属于
核心状态。若由 `semanticState` 声明，则应将其保存在 `pc` 中，并且
仅在成功的落子事件发生时更新。

## 5.9 独立标识符

以下标识符具有独立的版本控制：

- 规则集：游戏过程转换；
- 状态配置文件：位置字段与编码；
- 键配置文件：MPK 投影与规范化；以及
- 格式签名：外层线上文法。

从 D4 到 16-transform MPK 配置文件的变更不得要求规则集
版本变更。serialization-profile 的变更不得静默地改变游戏
规则。

# 6 `mill24-state-v1` 状态配置文件

## 6.1 概述

`mill24-state-v1` 是本版本指定的 状态配置文件。它适用于附录 A 中的 24 个公共点位。

配置文件边界包括下列序列化棋盘字符及其行为。实现可以采用不同的内部
表示，但在交换边界必须保留这些区别。

其有序字段为：

1. 棋盘;
2. 侧;
3. 阶段;
4. 动作;
5. 手中棋子;
6. 义务;
7. 无进展;
8. 主步;
9. 终局结果；以及
10. 零个或多个命名的语义或私有扩展。

## 6.2 棋盘

棋盘应由三个八个点位的环按此顺序组成：

```text
a7 d7 g7 g4 g1 d1 a1 a4 /
b6 d6 f6 f4 f2 d2 b2 b4 /
c5 d5 e5 e4 e3 d3 c3 c4
```

该显示中的空格仅用于解释说明。

字符应具有表 1 中的含义。

**表 1 — 棋盘字符**

| 字符 | 含义 |
|---|---|
| `W` | 活的白棋子 |
| `B` | 活的黑棋子 |
| `.` | 空且可用的点位 |
| `w` | 原属于白方的被阻挡的延迟移除标记 |
| `b` | 原属于黑方的被阻挡的延迟移除标记 |

表 1a 汇总了配置文件必须保留的行为。

**表 1a — 棋盘字符的派生行为**

| 字符 | 占据点位 | 可作目的地 | 可移动 | 可成磨 | 可作移除目标 | 计入活动物料 |
|---|---:|---:|---:|---:|---:|---:|
| `W`、`B` | 是 | 否 | 是，但受规则约束 | 是 | 是，但受规则与成磨吃子保护约束 | 是 |
| `w`、`b` | 是 | 否 | 否 | 否 | 否 | 否 |
| `.` | 否 | 是 | 否 | 否 | 否 | 否 |

小写标记应保留被移除棋子的所有者，并且仅在规则集选择的边界处清除。

像 `X` 这样没有所有者的遗留标记没有直接表示。转换器应从权威数据中
取得其所有者；否则应报告 `unrepresentable-under-profile`，且不得输出
貌似有效的目标记录。

## 6.3 方、阶段与动作

`side` 应识别执行下一个游戏动作所需的行动方。
它应仅在终止状态下为 `-`。

阶段值应为：

| 数值 | 含义 |
|---|---|
| `p` | 当前规则转换的落子机制 |
| `m` | 当前规则转换的移动机制 |
| `o` | 游戏结束 |

不存在 `ready` 阶段。正常的初始局面是 `p` 阶段，且
`primary-ply` 为零。

动作值应为：

| 值 | 含义 |
|---|---|
| `p` | `p` 阶段的主输入；规则集可允许落子、移动或两者皆可 |
| `m` | `m` 阶段的移动主输入 |
| `r` | 补充移除输入 |
| `o` | 无游戏过程输入 |

相位与动作是直接、分离的状态。两者均不应仅仅因为
通用的规则集能够推导出它们而被省略。

非平凡有效组合的示例包括：

- 阶段`p`, 动作`r`, 活跃手零：最终落子创建了一个
未解决的移除;
- 阶段 `m` 当对手仍有手中棋子时：不对称的手中棋子
耗尽能够使行动方在全局落子之前移动
边界；以及
- 在允许在落子时进行移动的规则集中的 `p` 阶段。

普通逻辑回合流程为：

```text
主动作
  |
  +-- 无义务 -----------------------------+
  |                                      |
  +-- 义务未决 -> 移除 -> 可能继续移除 ---+
                                         v
                              确定性稳定边界处理
                                         |
                                  下一个主动作
```

图中的未决状态使用动作 `r`。规则集可以产生零次、一次或多次补充移除；
在所选分支耗尽并运行稳定边界管道之前，不得开始下一个主动作。

## 6.4 手中棋子、计数器与终局结果

`hands` 应包含当前白方和黑方的**未落子储备**数量（传统上称为“手中
棋子”）。它是直接状态，不得从落子历史中重构。

`no-progress`应包含当前规则集计数器。一个待移除的棋子可以在下一次行动时被移除。
因此应保留计数值的当前值
主动作; 后续移除可以重置它。

`primary-ply`应在当前事件之前计算成功的位置和移动事件。
状态。移除事件不得增加它。创建该主动的主要行动
一个尚未解决的义务已经包含。

应在游戏进行时，`outcome`被`-`。游戏结束后，终局结果应为`w:<reason>`, `b:<reason>`或`d:<reason>`.

## 6.5 义务

义务字段应为`-`,或一个或多个替代义务分支。垂直线(`|`)隔开分支；分号(`;`)隔开同一分支中的连续义务。

义务记录是：

```text
actor:cause:zone:target-owner:remaining:targets:after
```

组件应具有表 2 中的含义。

**表 2 — 义务组件**

| 组件 | 值 | 含义 |
|---|---|---|
| `actor` | `w`, `b` | 应执行移除的玩家 |
| `cause` | 附录 B 原因 | 创建上下文的机制 |
| `zone` | `b`, `h` | 板子或手中棋子 |
| `target-owner` | `w`, `b` | 可移除令牌的所有者 |
| `remaining` | 正整数 | 该记录中的剩余移除次数 |
| `targets` | 六位十六进制数字集，`-`或`~` | 板头目标、手标记或延迟非板头目标 |
| `after` | `w`, `b`, `q` | 下一主动玩家，或继续下一个分支中的下一个义务 |

同一分支内的顺序是语义上的。分支按其第一个义务的规范原因顺序从表 B.1 中排序，然后按其完整的 US-ASCII 序列化。

每个分支中的第一义务应有相同的执行者。`side`应等于该执行者，`action`应为`r`.

应遵守棋盘义务的头部分支：

- `zone`应为`b`;
- `targets`不得为零;
- 每个目标位应当前包含由`target-owner`所有的活棋子; 和
- `remaining`不应超过机制仍要求的不同移除数量。

应在同一分支中的后续棋盘上出现的义务，`targets`应为`~`.
其目标集尚未存在，因为前置移除可能会改变这一点
应设定。`~`标记是明确的确定性延迟，不是允许
猜测缺失的导入状态。 当记录成为分支头时，11.11
应在另一个事件之前将`~`替换为一个非零的位集
应接受。分支头不得包含`~`。

对于手中棋子的义务：

- `zone` 应为 `h`；
- `targets` 应为 `-`；并且
- 目标所有者的手中棋子数应至少为 `remaining`。

应有一个义务，其`after`为`q`,在同一分支中，后面还有另一个义务。应有一个义务，其`after`为`w`或`b`,是其分支中的最后一个义务。

当选定的目标属于多个分支头时，规范顺序中的第一个分支获胜。其他分支被丢弃。这条规则使导入状态和第一移除确定。

## 6.6 语义扩展

应表3中列出的语义扩展。

**表 3 — 语义扩展**

| 键 | 语义特征 | 值 |
|---|---|---|
| `lm` | `last-mill` | 白色 `from,to`, 黑色 `from,to`, 使用 `-` 表示无 |
| `pc` | `placement-count` | 白色和黑色历史成功的落子 |
| `ul` | `used-lines` | 每个玩家磨坊线路位元集 |

如果 `semanticState` 声明了一个特性，其映射的扩展应发生，即使其值为零或 `-`。

`ul` 记录线路ID，而不是用于线路的点的并集。点的并集不能区分所有历史，且不得用于实现一次-per-line 语义。

`pc` 只在成功 `place` 事件时才会增加。从手中或棋盘上移除一个棋子不会减少它。

## 6.7 状态一致性

符合标准的消费者应强制执行以下内容：

a) 运行状态应具有侧面 `w` 或 `b`, 阶段 `p` 或 `m`, 结果 `-`;

b) 终局状态应具有侧面 `-`, 阶段 `o`, 动作 `o`, 义务 `-` 和非空结果;

c) 义务 `-` 意味着在阶段 `p` 或阶段 `m` 中应有动作 `p` 或动作 `m`;

d) 非空义务意味着应有动作 `r`, 且侧面等于每个分支头角色;

e) 玩家的活棋子、延迟令牌和手中棋子总数不得超过其初始令牌数量;

f) 只有规则集选择 `mark-opponent-board-until-moving` 才允许使用延迟令牌;

g) manifest 所需的每个语义扩展都应存在;

h) 未在 manifest 声明的标准语义扩展不得影响游戏或合法状态相等性;

i) 重复的扩展键无效;

j) 扩展键按升序排列，使用 US-ASCII 编码;

k) 权威字段中的值不会被更改为与派生缓存一致;

l) 规则集上下文和本地解析的清单在 ID 和版本上应一致，任何由外部或调用者提供的预期摘要应与该清单一致;

m) 当 MFEN 作为独立位置被消耗时，在进行中的稳定边界处应同步行动方（见 11.12）；

n) 当 MFEN 作为独立位置（而不是 MSTATE `origin` 或 `current` 字段）被消耗时，进行中的稳定边界处的 MFEN 应是可从该 MFEN 和其提供的规则集上下文中单独评估的每个确定性 11 条款转换的固定点，排除重复。

排除重复项（n）中的重复历史，因为独立的 MFEN 不携带重复历史。如果可预测处理会使状态终止，则拒绝它作为 `automatic-terminal-ongoing`。如果可预测处理会清除令牌、创建义务、改变方或以其他方式留下不同的进行中的状态，则拒绝它作为 `unstabilized-boundary`。

一个状态配置文件`origin`可能在此处理之前正在进行。重放器应在种子历史和事件之前应用11.20，然后将结果的终止、待定或可索取状态运载到`current`,见9.12。

# 7 MFEN/0.4 — 瞬时局面

## 7.1 目的

MFEN/0.4应代表由`mill24-state-v1`定义的精确瞬时状态。其规则语义来自提供的上下文。它能够表示稳定位置和可复制的中期义务位置。

MFEN不包括规则集标识或版本、清单摘要、事件历史、重复观察、和棋提议历史或来源。这些属于提供的上下文或MSTATE。一个无上下文的MFEN可以结构化地解析，但不能语义验证。

因此，复制或保存供以后语义使用的 MFEN 时，必须同时复制或保存完整的
`ruleset-id@version` 上下文。`g`、`r`、“German（德国）”、
“Russian（俄罗斯）”或“English（英国）”等标签不能替代已注册且带版本
的身份。

## 7.2 语法

规范ABNF在附录C和机器可读的`conformance/mif-0.4.abnf`文件中。

字段顺序是：

```text
MFEN/0.4 <state-profile> <board> <side> <phase> <action>
<hands> <obligations> <no-progress> <primary-ply> <outcome>
[<extension> ...]
```

显示仅用于可读性。一个MFEN记录是一个逻辑行。

## 7.3 规范化序列化

生产者应:

- 使用精确的签名 `MFEN/0.4`;
- 使用附录 A 板子顺序;
- 使用小写十六进制数;
- 使用最短允许的无符号十进制整数;
- 序列化一个缺失的义务和持续的结果为 `-`;
- 序列化每个分支在语义顺序中，并且替代分支按照规范顺序排列; 和
- 按照键对扩展字段进行排序。

应没有重复的扩展键。

一个空的私有扩展值是语法上有效的：

```text
x-note=
```

是否这样的值具有意义由其私有规范定义。

## 7.4 示例

示例使用符合性集合中由调用方提供的临时夹具清单。7.4.1 至 7.4.6 的
上下文依次是 `x-mif-fixture-nmm@2`、`x-mif-fixture-nmm@2`、
`x-mif-fixture-dooz@2`、`x-mif-fixture-delay@2`、
`x-mif-fixture-stateful@2` 和 `x-mif-fixture-nmm@2`。这些身份故意
不在 MFEN 记录中重复。

### 7.4.1 初始位置

```text
MFEN/0.4 mill24-state-v1 ......../......../........ w p p 9,9 - 0 0 -
```

### 7.4.2 等待棋盘移除

白方已经完成了主动作。棋盘目标集合中包含两个黑子，下一次主动玩家是黑方。

```text
MFEN/0.4 mill24-state-v1 WWW...B./......B./........ w p r 6,7 w:mill:b:b:1:004040:b 0 5 -
```

应不静默地将该状态转换为移除后状态。

### 7.4.3 等待手中棋子移除

手中棋子计数仍然显示黑方的令牌，因为补充性手中棋子移除尚未发生。
成磨后移除对手储备棋子是规则集变体，而不是标准九子棋规则；因此本例
使用对角线 `x-mif-fixture-dooz@2` 夹具。

```text
MFEN/0.4 mill24-state-v1 WWW...../B......B/........ w p r 9,10 w:mill:h:b:1:-:b 0 5 -
```

移除后，黑方的手中棋子数量为9。该状态不声称黑方落子了三个令牌；历史落子不可推断出来。

### 7.4.4 延迟标记

应为小写的 `b` 是不活跃的，保留所有权，并被阻止：

```text
MFEN/0.4 mill24-state-v1 WWW...../b......B/........ b p p 9,10 - 0 5 -
```

### 7.4.5 选择分支和序列依赖字段

```text
MFEN/0.4 mill24-state-v1 BWBW.WB./.W.W..B./.W...... w p r 3,5 w:intervention:b:b:2:000005:b|w:custodian:b:b:1:000040:b|w:mill:b:b:1:004000:b 7 20 - lm=-,-;-,- ul=0000,0000
```

第一个选定的目标将承诺其中之一的三个分支。

### 7.4.6 对手仍有储备时进入移动阶段

白方没有未落子储备，故其阶段为 `m`；黑方仍有一个储备棋子，轮到黑方
时其阶段为 `p`。阶段与当前行动方同步，不能由对手的手中数量推断。

```text
MFEN/0.4 mill24-state-v1 WWW.BBB./......../........ w m m 0,1 - 0 17 -
```

## 7.5 规则集上下文和完整性元数据

MFEN 不携带规则集身份或清单摘要。 在语义验证之前，调用者应提供：

```text
(ruleset id, ruleset version)
```

两项都不可缺少。裸的地域、语言或社区标签、无版本 ID 或单字母应用代码
均不足以提供语义上下文。

消费者应使用该身份向调用方提供的本地清单解析器进行查询。 消费者不得自动访问网络。 应用程序可以定义文档化的 UI 默认值，但该默认值不是 MFEN 的一部分，并且不应由无上下文交换验证器推断。
该 UI 应显示最终解析出的完整身份，不得把默认值说成 MFEN 本身编码的事实。

缺失的规则集上下文或无法定位其清单是 `manifest-missing`。 多个不同的本地清单声称相同的 ID 和版本是 `manifest-conflict`。 当一个信封 或调用方提供预期摘要时，提供的清单，其 JCS 摘要与之不同，是 `manifest-digest-mismatch`.

MSTATE 是标准自包含的信封，用于携带私有清单及其摘要。 另一传输可能提供等效完整性元数据，但该元数据不在 MFEN 之外，并且不会改变规范化的 MFEN 序列化。

# 8 MPK/0.4 — 应用稳定结构分析键

## 8.1 目的和限制

MPK/0.4 提供了一个明确键配置文件下的结构分析的稳定文本键。

MPK 故意省略：

- 无进展;
- 主要木板;
- 重复多重性和观察历史;
- 声称和和棋提议;
- 最终结果; 和
- 事件来源。

它适用于结构分析数据集和表格库样式数据集 **仅当所选键配置文件完全捕获数据集的状态等价性时**。

## 8.2 资格

一个 MFEN 只有在以下条件下才适用于本版中的结构配置文件：

a) 应为结构上有效。

b) 运行中。

c) 义务`-`;应

d) 行动是`p`应或`m`;应

e) 规则集所需的每个语义扩展都被键配置文件理解。

f) 每个影响合法游戏的私有扩展都在键配置文件中注册了一个规范化转换。

g) 应用程序不将省略的裁决状态视为其等价关系的一部分。

对于 `structural-aut16-v1`，应用程序还必须具备 8.4.2 所要求的外部
环交换不变性声明。

未解决的移除不合格。生产者不得自动完成它以获得一个关键。

## 8.3 语法和投影

规范 ABNF 在附录 C 中。

```text
MPK/0.4 <state-profile> <ruleset> <key-profile> <board24>
<side> <phase> <hands> [<key-extension> ...]
```

`board24` 是三个 MFEN 环的连接，`/` 不包括在内。

投影应包含：

- 状态配置文件；
- 规则集；
- 键配置文件；
- 板子，包括延迟令牌；
- 方面；
- 阶段；
- 直接手中棋子；
- 从 `semanticState` 映射的每个扩展；
- 由键配置文件要求的任何理解私有语义扩展。

与 MFEN 不同，MPK 通过 ID 和版本来识别规则集，因此来自不同规则集的键不会冲突。 MPK 生产者投影一个 MFEN 时，应从 MFEN 的调用方提供的上下文中复制其身份。 MPK 没有清单摘要； 数据集或包含的信封可以将其身份绑定到外部的摘要。

MPK 应包含由键配置文件和规则集语义状态映射为该键所选定的扩展。 私有非语义扩展不得出现在 MPK 中。 私有语义扩展仅在键配置文件定义投影、规范表示、点/线转换和比较语义时才会出现。

派生活跃计数不得重复。 历史落子计数只发生在 `placement-count` 声明且 `pc` 因此是语义的。

## 8.4 注册键配置文件

### 8.4.1 `structural-d4-v1`

该配置文件使用表 A.3 中的八个视觉几何变换。它不声称是顶点自动同构群的完整拓扑。

### 8.4.2 `structural-aut16-v1`

该配置文件使用表 A.3 中的八个 D4 变换和与外环/内环交换组合的相同八个变换。

环交换保留了本版中两种拓扑的所有注册磨坊线的邻接关系。

仅保持图结构并不能证明游戏状态等价。只有外部的、带版本的声明明确
说明外环/内环交换保留已解析规则集和数据集中的全部规则相关特征时，
才能对该规则集使用此配置文件。该声明属于配置或数据集元数据，绑定到
完整规则集身份，不是 MRS 字段；生产者不得仅根据拓扑推断它。

使用此配置文件的数据库应在元数据中记录键配置文件 ID 以及该声明的
身份或版本。除非置换表采用相同的已声明等价关系，否则它不是通用的
置换表键。

## 8.5 规范化算法

对于配置文件中的每个变换，生产者应：

1. 将每个棋盘点位转换;
2. 转换 `lm` 和任何注册坐标扩展中的每个坐标;
3. 通过选定的拓扑结构将 `ul` 中的每个置位转换为线路排列;
4. 保留像手中棋子和 `pc` 这样的颜色特定值与其颜色相关联;
5. 根据注册转换每个理解的私有语义扩展;
6. 序列化完整的 MPK 候选项并规范化; 和
7. 比较候选者的 US-ASCII 八进制字节序。

最小的完整候选者应为 MPK。

如果多个转换产生相同的最小候选者，则选择具有最低配置顺序的转换来将移动和坐标映射回源框架。

当存在转换语义扩展时，不应在棋盘上进行比较。

## 8.6 移动和结果坐标

与 MPK 关联的应用程序将移动、主要变体或注释记录到选定的转换中，或者保留可逆的框架映射。

使用标准化键存储的坐标位于标准化帧中。直接将它们作为源帧中的移动返回是互操作性错误。

与 MPK 正规化动作相关联的任何线路标识符，包括 `interventionLine` 在位置或移动事件上，应使用选定的拓扑结构的同一选定转换的线路排列进行转换。

## 8.7 示例

宜将白棋放在源坐标 `d7` 上，源棋盘如下：

```text
.W......................
```

在 `structural-d4-v1`, 最小棋盘将其落子在 `a4`。

```text
MPK/0.4 mill24-state-v1 x-mif-fixture-nmm@2 structural-d4-v1 .......W................ b p 8,9
```

在 `structural-aut16-v1`, 环交换扩展轨道， 最小棋盘将其落子在 `c4`。

```text
MPK/0.4 mill24-state-v1 x-mif-fixture-nmm@2 structural-aut16-v1 .......................W b p 8,9
```

该 Aut16 示例假定存在 `MPK-VALID-0003` 记录的带版本外部夹具声明。
这些是故意不同的键。数据库应确定它使用的键配置文件。

语义状态也参与比较。对于 `MPK-VALID-0004` 使用的
`x-mif-fixture-stateful@2` 源：

```text
MFEN/0.4 mill24-state-v1 W.W.W.../B.B.B.../........ w m m 0,0 - 4 18 - lm=d1,d7;-,- ul=0003,0000
```

`r90cw` 与 `mirror-h` 具有相同的最小棋盘字符串，但变换后的状态不同：

| 变换 | 棋盘 | `lm` | `ul` |
|---|---|---|---|
| `r90cw` | `..W.W.W...B.B.B.........` | `a4,g4;-,-` | `0006,0000` |
| `mirror-h` | `..W.W.W...B.B.B.........` | `d7,d1;-,-` | `0006,0000` |

完整候选比较选择 `r90cw`；只比较棋盘会丢弃权威信息。

# 9 MSTATE/0.4 — 可恢复游戏状态

## 9.1 目的

MSTATE/0.4 表示：

- 一份准确的起始MFEN;
- 用户或裁判事件的有序序列;
- 当前的准确MFEN检查点;
- 活动重复观察窗口; 和
- 可审计的和棋声明和和棋记录。

一个MSTATE可以在等待义务时结束。因此，用户可以拷贝、粘贴并恢复中间移除选择状态。

## 9.2 JSON, I-JSON 和 JCS

一个MSTATE及其嵌入的每个MRS清单应符合RFC 8259和RFC 7493 I-JSON规范。

此外：

a) JSON转义解码后对象成员名称应唯一;

b) 未配对的Unicode surrogate将被拒绝;

c) 精确整数应符合5.3。

d) 字符串不得在解析、哈希或序列化过程中进行Unicode规范化。

e) 应使用RFC 8785 JCS规范化的MSTATE和清单字节。

f) 一个解析器应检测到在转换为可能丢弃它们的map之前的名称重复。

应接受漂亮打印的JSON作为输入，规范输出和摘要输入应为JCS。

## 9.3 必需的顶层成员

应包含在MSTATE对象中标准成员表格中的所有成员，及其允许的`x-`成员。

**表 4：MSTATE 成员**

| 成员 | 类型 | 含义 |
|---|---|---|
| `format` | string | `MSTATE/0.4` |
| `positionFormat` | string | `origin` 和 `current` 的格式；本版为 `MFEN/0.4` |
| `stateProfile` | string | 嵌入局面所使用的状态配置文件 |
| `ruleset` | object | 规则集身份、摘要以及可选或必需的清单 |
| `origin` | string | 规范起始 MFEN |
| `events` | array | 有序事件序列 |
| `current` | string | 规范重放检查点 |
| `repetitionHistory` | array | 有序的有效重复窗口 |
| `preOriginClaims` | array | 起点边界处的声明审计种子 |
| `claims` | array | 有序的和棋提议与声明审计记录 |

`positionFormat` 确定了 MSTATE 版本。 未来的一版 MSTATE 可以支持另一种位置格式，而不假设 MSTATE 和 MFEN 版本是独立的，同时静默地将其中之一硬编码。

在 `origin` 和 `current` 中，状态配置文件应与顶级 `stateProfile` 成员匹配。 顶级 `ruleset` 对象为两种位置提供规则集上下文；该身份在 MFEN 内部不会重复。

## 9.4 规则集成员和清单外壳

`ruleset` 对象应包含：

- `id`;
- `version`;
- `digest`；以及
- `manifest`, 当本子节要求时。

对于一个 `x-` 规则集，`manifest` 应存在。 对于一个注册的公共规则集，它可以在当地解析器返回精确 `(id, version, digest)` 对象时省略。

当 `manifest` 存在时：

- 它应符合 MRS/0.4;
- 其 `id` 和 `version` 应与包含的成员匹配；
- 其 JCS SHA-256 应与 `digest` 匹配；以及
- 它应在验证成功后用于重放。

应提供的摘要提供完整性识别，不提供真实性或发布者信任。

## 9.5 事件序列和常见要求

每个事件应为一个对象：

- `seq`,一个整数;
- `actor`, `w`, `b` 或 `system`; 和
- `type`,一个注册事件类型。

事件应包含其类型所需或允许的标准成员，plus零个或多个`x-`成员。 除非外部规范明确声明否则，`x-`成员是非语义元数据。 生产者不得使用 `x-` 成员来改变标准事件的游戏效果。

`events` 是一个有序历史记录，而不是集合。 `seq` 值应为从 1 开始的连续整数。 数组顺序应等于 `seq` 顺序。

事件应逐一应用。 每个事件后，应在下一个事件验证之前执行每个确定性效果 (条款 11)。

游戏事件的行为者验证应为类型特异的：

- 应为 `place` 或 `move` 事件的行为者等同于 `side`;
- 应为 `remove` 事件的行为者等同于 `side`, 并且每个选择分支头部的行为者; 和
- 其他玩家事件应满足9.8节中事件特定行为者的规则。

应不得进行`system`、`place`, `move`, `remove`等事件，包括和棋谈判或投降声明。

应为未知事件类型被拒绝。一个`x-`游戏事件应
也应被拒绝，除非：

a) 有一个外部语义事件规范被明确标识;

b) 消费者实现了它; 和

c) 规则集授权它。

未知的游戏事件绝不应被忽略，好像是非语义私有成员。

## 9.6 主要游戏事件

### 9.6.1 落子

```json
{"seq":1,"actor":"w","type":"place","at":"a7"}
```

`actor`应是行动方。`at`应是合法的、可用的点位。
应触发事件，增加主动行数，并在语义为`placement-count`时，
该玩家`pc`的。

当为阶段 `p` 启用干预吃子时，一个落子事件也可能包含 `interventionLine`, 表示表A.2中的第2行ID。缺省选择第一条候选线。成员应仅在事件创建多于一条候选线且其值指向非第一条候选线时存在。命名默认线是非规范化的；命名外部候选集之外的线是不合法的。

### 9.6.2 走子

```json
{"seq":19,"actor":"w","type":"move","from":"a7","to":"a4"}
```

应为 `from` 和 `to` 的合法移动。事件将增加主回合数。

当干预吃子为阶段的适用阶段启用时，一个移动事件也可能包含 `interventionLine`，遵循9.6.1相同规则。

## 9.7 `remove` 事件

应为移除事件具有结构化的 `target`.

应遵循棋盘移除规则。

```json
{
  "seq": 6,
  "actor": "w",
  "type": "remove",
  "target": {
    "zone": "board",
    "at": "b6"
  }
}
```

手中棋子移除。

```json
{
  "seq": 6,
  "actor": "w",
  "type": "remove",
  "target": {
    "zone": "hand",
    "player": "b"
  }
}
```

行动方应匹配每个分支头。目标应选择一个分支头中的目标。

对于棋盘目标，目标位应设置，活跃的所有者应匹配分支头。对于手中目标，分支头应具有区块 `h`,其目标所有者应等于 `player`,并且 `targets` 应为 `-`.

事件上直接落子的遗传形状 `"at":"b6"` 是无效的。

手中棋子移除不是 `place` 的自动隐式副作用。创建手中棋子义务的事件是 place 事件；remove 事件减少手中棋子数量。

## 9.8 和棋、投降和裁判事件

标准非棋盘事件包括：

| 类型 | 行动方 | 必要的额外成员 | 效果 |
|---|---|---|---|
| `offer-draw` | 主动方 (`side`) | 无 | 开启提议 |
| `accept-draw` | 非提供方 | `offerEventSeq` | 通过协议同意终止游戏 |
| `decline-draw` | 非提供方 | `offerEventSeq` | 拒绝提议 |
| `withdraw-draw` | 提供方 | `offerEventSeq` | 撤回提议 |
| `claim-draw` | 主动方 (`side`) | `reason` (`no-progress` 或 `repetition`) | 只有当选择的声明条件当前满足时才接受 |
| `resign` | `w` 或 `b` | 无 | 对手通过投降获胜 |
| `adjudicate` | `system` | `result`, `reason`, `authority` | 终局外部裁决 |

和棋谈判不会改变方、阶段、行动、手中棋子、义务、无进展或主动步。

这些事件的行动方规则与 9.5 中的位置/移动/移除匹配独立：

- `offer-draw` 和 `claim-draw` 只能由 `side` 执行；
- `accept-draw` 和 `decline-draw` 可以由非提供方执行，因此可能有 `actor` 不等于 `side`；
- `withdraw-draw` 由提供方执行，可以在对手的回合中执行；
- `resign` 可以由任何玩家在任何状态下执行，包括移除义务尚未完成时；而且
- 当移除义务尚未完成时，`offer-draw`, `accept-draw`、`decline-draw`, `withdraw-draw` 和 `resign` 根据上述规则仍然允许；而 `claim-draw` 仍然受限于 `side` 和满足的声明条件。

应在由 `expired` 和 `draw.offers.expiry` 选择的边界处关闭交易。 `explicit-only` 不会自动将其过期，而是 `on-opponent-primary-action` 在对手成功落子或移动之前立即过期。

应在每个终局转换（除了`accept-draw`）关闭所有仍然打开的offer，并在终局规范化之前立即将其规范化为`expired`,而不是记录协议接受状态`accepted`.

最多只能有一个提议开放。新 `offer-draw` 在提议开放时无效。接受、拒绝或撤回操作应准确引用该开放提议。接受或拒绝方应为非提供方；撤回方应为提供方。

在 `automatic` 模式下，`claim-draw` 无效，因为条件已经结束游戏。在 `claim` 模式下，未满足的声明无效；它不会被记录为失败的游戏事件。

应为`adjudicate`, `result`应是`w`, `b`或`d`; `reason`应满足B附录中的要求;`authority`应是一个非空字符串。结果和原因成为终局MFEN结果。

`system` 受限于 `adjudicate`。不得落子、移动、移除、提出、接受、拒绝、撤回或宣布投降。

## 9.9 标记和延迟事件效果

`mark-opponent-board-until-moving` 不引入 `mark` 事件。

普通结构化棋盘 `remove` 事件是玩家动作。其规则集选择的效果将目标从 `W` 更改为 `w`, 或 `B` 更改为 `b`.

清除小写令牌是确定的转换在 `on-enter-moving-v1`；这不是事件。生产者不得插入 `clear-mark` 事件。

## 9.10 重放历史

### 9.10.1 一般

`repetitionHistory` 是当前有序观察窗口。它既不是无序集也不是实现哈希的数组。

每个条目应包含：

- `source`, 等于 `pre-origin`, `origin` 或 `event`;
- `eventSeq` 当源为 `event` 时；和
- `key`, 一个 `legal-state-v1` 对象。

前面的 `pre-origin` 条目导入历史。它们应在任何 `origin` 或 `event` 条目之前出现。其数组顺序是按时间顺序的。

当起源满足清单的观察边界时，会自动生成一个 `origin` 条目。当主动列达到的稳定状态被观察到时，`event` 条目标识了该列的最终事件。

### 9.10.2 `legal-state-v1` 键

键对象应包含：

- `stateProfile`;
- `ruleset`;
- `board`;
- `side`;
- `phase`;
- `action`;
- `hands`; 和
- `semantic`, 包含从 `semanticState` 映射的每个扩展以及其他游戏场景中没有其他任何场景的对象。

应排除的键包括 no-progress、primary-ply、outcome 和 claims。它是作为一个语义对象进行比较的；实现可以内部使用 JCS 字节对其进行哈希，但不得在 MSTATE 中替换为未文档化的哈希。

### 9.10.3 观察算法

对于 `stable-moving-v1`：

1. 使用前导 `pre-origin` 记录填充窗口;
2. 当出现列表中的重置事件或确定性触发器时，清除活动窗口之前的任何后续观察;
3. 不要在其义务队列非空时观察主动作;
4. 完成每个非重复确定性转换通过 11.20 步骤中的僵局步骤;
5. 如果结果起源是持续的，阶段 `m`, 动作 `m` 和义务 `-`, 追加一个 `origin` 观察;
6. 当主动序列首次达到稳定移动状态时，追加一个 `event` 观察并识别关闭序列的事件;
7. 如果发生次数达到配置值，则应用自动或声明语义; 和
8. 不要为重复决策引起的终局变异追加另一个观察。

导入的待处理起源不会在其义务关闭和稳定移动边界到达之前被观察到。

## 9.11 起点前声明种子和 `claims` 数组

`claims` 是一个审计投影，用于绘制和接受的和棋声明。它应在重放时重新构造并与提供的数组进行比较。

`preOriginClaims` 是一个单独的重放种子。每个种子记录应包含：

- `actor`,;
- `kind` 等于 `draw-offer`;
- `status`, 使用以下 offer 状态; 和
- 没有 `source`, `eventSeq` 或 `resolvedEventSeq`.

其数组顺序是按时间顺序。 最多一个种子 offer 可以具有状态 `open`.

每个 `claims` 记录应包含：

- `source`, 等于 `pre-origin` 或 `event` (省略的 `source` 表示 `event`);
- `actor`;
- `eventSeq` 当源是 `event` 时;
- `kind`, `draw-offer` 或 `draw-claim`;
- `status`; 和
- `resolvedEventSeq` 当分辨率在后续事件中发生时。

Offer 状态应为之一 `open`, `accepted`, `declined`, `withdrawn` 或 `expired`. 有效的和棋声明具有状态 `accepted`.

重放应复制每个`preOriginClaims`种子记录到初始审计
应为磨坊棋的规则集。`source=pre-origin`. 提供的`claims`数组
应以每个种子记录的精确一个最终投影开始，接着
由事件源记录。种子值是起始时间状态；`claims`值
应为重放后审计状态。

一个开放于起源的种子 offer 被后续 `accept-draw`, `decline-draw` 或 `withdraw-draw` 事件通过保留的 `offerEventSeq=0` 引用。当一个事件解析时，最后的投影应包含该事件的 `resolvedEventSeq`. 当确定性起源处理在事件 1 之前过期时，最终投影具有状态 `expired` 和没有 `resolvedEventSeq`.

事件源记录应按严格递增的 `eventSeq` 顺序排列。 `eventSeq` 在事件源记录中是唯一的。 同类多个记录允许，当它们指向不同的事件时。

JCS 不会重新排列数组；因此，这一排序规则对于语义规范化是必需的。

## 9.12 重放和检查点验证

重放器应：

1. 验证 I-JSON 而不丢弃重复名称；
2. 解析和验证清单；
3. 根据 6.7 解析和验证起源（除 (m) 和 (n) 项外，这些项仅适用于独立 MFEN 交换）；
4. 只取前导 `pre-origin` 重复条目作为初始历史记录；
5. 初始化声明审计从 `preOriginClaims` 开始；
6. 当起源是持续的并且义务为 `-`, 运行 11.20 的稳定边界管道（无论起源是否是重复观察边界），并在种子重复历史和声明审计后；
7. 应用每个事件和所有确定性转换；
8. 规范化结果 MFEN；
9. 与 `current` 比较字节对字节；
10. 将生成的重复数组语义比较与 `repetitionHistory`；以及
11. 将生成的声明审计语义比较与 `claims`。

持续待定起源不会通过 11.20 直到其选择的义务分支变空。当任意起源直接进入全局落子边界并且 `turn.placingEndActivePlayer=retain`, 保留意味着起源当前的 `side`。

不应修复不匹配。应将其报告为 `checkpoint-mismatch`, `repetition-history-mismatch` 或 `claims-mismatch`。

符合性集合包括一个自包含的私有清单包裹，其重放结束于待移除状态。

# 10 MRS/0.4 —有限规则集清单

## 10.1 设计边界

MRS/0.4遵循有限机制方法。

一个MRS清单不是一般规则语言，也不是实现开关的集合。它只选择那些在第11条中定义了完整过渡、目标集、排序和裁决边界的机制。

MRS 选择机制，但不单独选择触发或终局优先级；这些优先级属于所标识的
语义配置文件。

具有语义超出这些机制之外的私有游戏需要单独识别的语义配置文件和规范。仅仅添加未知成员到`mif-finite-rules-v2`并不使该游戏通过符合性实现可重放。

## 10.2 必要成员

一个MRS清单应是一个I-JSON对象，包含表格5中的成员。

**表格5 — MRS成员**

| 成员 | 类型 | 含义 |
|---|---|---|
| `format` | string | `MRS/0.4` |
| `id` | string | 规则集标识符（不含`@version`） |
| `version` | 正整数 | 游戏语义版本 |
| `title` | string | 可读性强的英文标题 |
| `status` | string | `fixture`, `experimental`, `registered` 或 `deprecated` |
| `semanticsProfile` | string | `mif-finite-rules-v2` |
| `topology` | string | 注册拓扑 |
| `pieces` | object | 初始材料和损失阈值 |
| `turn` | object | 初始和落子结束控制 |
| `flying` | object | 飞行机制 |
| `placing` | object | 落子机制 |
| `mills` | object | 磨坊形成后果 |
| `captures` | object |有限捕获机制|
| `boardFull` | object | 全盘后果 |
| `stalemate` | object | 无法移动后果 |
| `draw` | object | 无进展、重复和提议规则 |
| `semanticState` | array | 必须的序列依赖状态特征 |

应在 MRS 清单中排除评估权重、搜索设置、UI 状态、动画、标记风格、数据库打包和网络位置等游戏语义。

## 10.3 规范化数组

JCS 保留数组顺序。因此，根据表 6 分类，每个 MRS 数组都有特定的含义。

**表 6 — MRS 数组语义**

| 数组 | 语义 | 规范化要求 |
|---|---|---|
| 吃子 `phases` | 集合 | 唯一、升序 ASCII |
| `countedPrimaryActions` | 集合 | 唯一、升序 ASCII |
| 和棋 `resetEvents` | 集合 | 唯一、升序 ASCII |
| `semanticState` | 集合 | 唯一、升序 ASCII |

MRS/0.4 清单没有依赖顺序的机制数组。在 `mif-finite-rules-v2` 内，
触发和终局优先级是配置文件政策，不是清单选项，也不是所有可能语义
配置文件的通用规则。不同优先级需要另一个明确标识的语义配置文件，
不得编码为含义不明的任意 MRS 数组。

## 10.4 拓扑、棋子和回合

应为 `topology`

- `mill24-orthogonal-v1`；或
- `mill24-diagonal-v1`。

`pieces`应包含：

- `white`,白方初始令牌数;
- `black`,黑方初始令牌数;和
- `minimumLive`,活棋子及手中棋子的最小值，若不足则不得继续游戏。

`turn`应包含：

- `initial`,`w`或`b`;
- `placingEndActivePlayer`,`w`,`b`或`retain`.

`retain`表示在全球落子界限被跨越时，前一个主动序列选择的玩家仍保持活跃状态。

## 10.5 飞行和落子

“落子机制（placing regime）”是双方未落子储备均归零（或早停将其归零）
之前的全局区间。在此期间，当前行动方的阶段按 11.12 同步；若其储备已
空而对手仍有储备，当前行动方的阶段可以是 `m`。

`flying`应包含：

- `enabled`, 布尔值; 和
- `maximumLive`, 正整数。

当启用时，处于阶段 `m` 的玩家，如果其活棋数量不超过 `maximumLive` 可以将一颗活棋移动到任意 `.` 点。延迟令牌点不是目的地。

例如 `maximumLive=3` 时，三枚活动棋子的行动方可移动到任意空点；
同一行动方有四枚活动棋子时仍受相邻限制，除非另一个机制适用。

`placing` 应包含：

- `movementAllowed`, 布尔值; 和
- `earlyStop`, 包含 `emptyPoints` 和 `boundary` 的对象。

`emptyPoints` 设为零会禁用早停。非零值在本版中仅支持：

```text
boundary = after-unobligated-place-v1
```

边界的精确位置见 11.12。

## 10.6 磨坊棋对象

`mills` 应包含：

- `placingEffect`；
- `movingEffect`；
- `removalMultiplicity`；
- `targetProtection`；
- `lineReuse`；
- `reverseReformation`；以及
- `delayedClearBoundary`。

`placingEffect`宜为：

| 值 | 含义 |
|---|---|
| `remove-opponent-board` | 形成方移除对手活棋标记 |
| `remove-opponent-hand-change` | 先移除对手手中棋子标记，超出后转为对手主动方 |
| `remove-opponent-hand-retain` | 同样目标顺序，然后形成方保持主动方 |
| `opponent-remove-own-board` | 对手移除对手自己的棋盘标记 |
| `mark-opponent-board-until-moving` | 棋盘移除改变目标为被阻挡的小写标记 |
| `remove-by-current-mill-count-at-placing-end` | 延迟特殊当前磨坊计数移除计算到全局落子边界 |

`movingEffect`应为`remove-opponent-board`在MRS/0.4中。

`removalMultiplicity`应为：

- `one-per-primary`；或
- `one-per-new-line`。

`targetProtection`应为：

- `outside-mill-first`；或
- `all-opponent`。

`targetProtection` 是保留的线格式标识符，其自然语言含义是
**成磨吃子保护**：只要存在磨外棋子，完整磨内的对手棋子是否受保护。

`lineReuse` 应为 `unlimited` 或 `once-per-player`。

`reverseReformation` 应为 `allowed` 或 `prohibit-immediate`。
该线格式标识符的自然语言含义是**立即反向重组**，即 11.5 规定的移出后
立即移回成磨模式。

应存在 `delayedClearBoundary` 和 `on-enter-moving-v1`,即使落子效果不创建延迟令牌时也应存在。

## 10.7 吃子对象

`captures` 应包含：

- `resolution`,等于 `target-commits-v1`;
- `custodian`;
- `intervention`; 和
- `leap`.

每个捕获机制对象应包含：

- `enabled`,布尔值;
- `lines`,具有布尔值 `squareEdges`, `cross` 和 `diagonal` 的内容;
- `phases`,包含 `moving`, `placing` 或两者的集合; 和
- `maximumOwnLivePieces`,正整数或 `null`.

该对角线家族在`mill24-orthogonal-v1`上是空的，即使它的布尔值为真。

应由监管者和干预者在`maximumOwnLivePieces`阶段`m`中应用。对于跳跃，它将在列出的每个阶段中应用。`null`意味着没有材料限制。

禁用的机制应保留所有成员，使得清单具有一个规范的形状，但其它值对游戏无影响。

## 10.9 和棋对象

# 11 `mif-finite-rules-v2` 过渡语义

## 11.1 初始状态

除非应用程序故意提供另一个起源，manifest的正常初始状态应有：

- 所有点 `.`;
- 手中棋子等于 `pieces.white,pieces.black`;
- 侧数等于 `turn.initial`;
- 阶段 `p`;
- 行为 `p`;
- 义务 `-`;
- 无进展零;
- 主动行棋次数零;
- 结果 `-`;
- 必须的线路和落子计数器零;
- `lm=-,-;-,-`.

## 11.2 主要事件验证

只有在稳定状态时，才会接受主要事件。

对于 `place`：

- 行为应为 `p`;
- 行动者至少有一个手中棋子标记;
- 目标是 `.`;
- 手中棋子减少；和
- 活动棋子落子。

对于 `move`：

- 行为应为 `m`, 或行为 `p` 与
  `placing.movementAllowed=true`;
- `from`包含行动者的活棋子;
- `to`应为 `.`;
- 移动除非飞行或启用跳跃时，否则必须相邻；和
- 反复形成规则允许它。

应在物理变换成功后，主动作的第一步增量。
无进展和 `pc` 随后被更新为已声明的值。

## 11.3 触发检测顺序

在成功的落子或移动之后，应从行动后的棋盘中按照以下顺序检测触发：

1. 端点到端点移动的跳跃捕获；
2. 目标通过目的地形成的可用磨坊线路；
3. 干预捕获；
4. 守护者捕获。

这是一个检测顺序。分支构造和重叠目标解决方案在 11.8 中指定。

如果跳跃至少有一个合法目标，跳跃是该主动作的独占：磨坊、干预和守护者分支不会生成。检测可用磨坊仍然是一个语义事件： 11.4 还会更新 `lm` 和 `ul`, 并且 `mill-formation` 会在配置时重置无进展。
因此，跳跃独占只抑制竞争的移除分支，不抑制成磨事件或其配置的无进展重置。

## 11.4 主动作形成的磨坊线

一条线由主动作新形成，当：

- 所有三条线点都包含行动方的活棋子;
- 目标属于线路; 和
- 线路不被 `lineReuse` 过滤。

对于 `once-per-player`, 一条线如果在该玩家的 `ul` 中已经设置了位，则不可用。同一线的另一玩家位是独立的。

`one-per-primary` 在至少有一个可用的线路存在时产生一项磨坊移除义务。 `one-per-new-line` 对每个可用线路产生一项移除。

例如，在 `W.W...../.W....../.W......` 上落到 `d7`，会同时形成线 0
（`a7,d7,g7`）和线 12（`d7,d6,d5`）。`one-per-primary` 的普通成磨
分支剩余 1 次移除；`one-per-new-line` 则剩余 2 次，并按 11.9 受可用
目标物料上限约束。

当可用线路触发时：

- 其每个玩家的 `ul` 位是当 `used-lines` 是语义的时设置; 和
- `lm` 设置为动作的 `from,to` 为移动, 或 `-,to` 为落子,
  当 `last-mill` 是语义的时。

每次成功的主动作形成无用磨坊后，清除行动方的 `lm` 项至 `-,-` 时，若 `last-mill` 是语义。这适用于移动和落子。

## 11.5 立即反转重组

与 `prohibit-immediate`, 提议的移动 `from -> to` 只有当以下所有条件成立时才被禁止：

a) 该行动方的 `lm` 等于 `to,from`。

b) 当前位于 `from` 的棋子至少属于一个可用的完整磨坊。

c) 释放 `from` 并占据 `to` 将形成至少一个可用的磨坊。

使用 `once-per-player`, 一条已经使用的线路在此测试中不是“可用”的。

## 11.6 普通磨坊移除目标

对于 `all-opponent`，目标集是每个对手的活棋子。

对于 `outside-mill-first`：

1. 计算任何当前完整对手磨坊中的对手活棋子的并集。
2. 如果有任何对手活棋子位于该并集中之外，只有外部棋子才是目标；否则
3. 每个对手活棋子都是一个目标。

因此该保护是优先规则而非绝对免疫。若对手所有活动棋子都在完整磨内——
例如恰为 `a7,d7,g7`——步骤 3 使三枚棋子全部成为合法目标。

延迟标记和手中棋子标记不是棋盘目标。

对于 `opponent-remove-own-board`, 目标所有者和行动方是对手。每个对手活着的棋子都是一个目标；普通的对手-磨坊保护不适用于选择自己的令牌。

## 11.7 捕获机制

捕获机制使用表A.2中的有序线族。

### 11.7.1 保管人

保管人是触发在一条线 `[a,m,b]` 上，当主动作结束于 `a`，且行动方已经占据 `b`, 或结束于 `b`，且行动方已经占据 `a`, 而 `m` 中包含对手活着的棋子。

所有符合条件的中点都被收集并过滤掉普通的磨坊移除保护。分支有原因 `custodian`, 剩余 1 和结果目标集合。

### 11.7.2 干预

应在主动作结束于中点`m`时触发干预
应包含`[a,m,b]`和两端的对手活棋。

候选线路按照表A.2的顺序排列。如果引起此次事件的主要事件有一个`interventionLine`, 则选择该候选线路；否则选择第一条候选线路。

在选择线路后，普通磨坊保护措施应施加。如果两端点都被过滤掉，则干预不会触发，算法不得回退到较晚的线路。

该分支有原因`intervention`,剩余活棋等于存活端点数目，目标等于这些端点。两端点中第一个被移除后，只有配对端点仍然是目标。

### 11.7.3 跳跃

跳跃适用于从`[a,m,b]`的两端点之一移动到另一端点时：

- 目的地是`.`;
- `m`包含对手活棋;
- 配置的阶段、线路家族和材料限制允许跳跃; 和
- 中间棋子生存普通磨坊保护。

移动和吃子仍然是单独事件。移动创建一个专属原因`leap`的棋盘移除分支，剩余1个目标为`m`.

## 11.8 分支构造和目标承诺

如果触发了闰年，唯一的分支就是闰年。

应在规范化的原因顺序中构造非空分支。

1. 干预
2. 守护者
3. 磨坊

应为吃子分支的结尾是下一名主动玩家的对手。

应使用 11.9 或 11.10 的分支，且可以包含多个分号分隔的
义务。其最终`after`由选择的落子或
移动效果。该分支中的早期义务使用`after=q`>。

每个分支头的棋盘义务都与其当前目标位相对应。之后的所有棋盘义务都将目标设置为`~`,直到11.11促进它。手中棋子义务始终使用`-`.

每个第一条分支的义务都有相同的行动方，除非违反 10.11 的组合。

应发布所有分支，分支之间用 `|` 分隔。第一个移除目标选择规范化顺序中的第一个匹配分支，每个其他分支在应用移除之前都被丢弃。

这个目标提交规则是规范性的。实现不得将从替代捕获上下文中添加的计数视为所有替代都是顺序的。

## 11.9 落子阶段的磨坊效果

让 `R` 成为磨坊移除多重性。对于由本子句或 11.10 创建的普通磨坊棋盘移除序列，剩余部分应等于 `min(R, number of live board tokens owned by the target owner)`。当前头目标集仍然在 11.6 下计算，并且在每次移除后重新计算。保护后扩展的目标集因此仍可供同一序列使用。零计数板义务不得创建。

机制特定捕获分支保留自己的有限容量：干预使用其存活端点，监护和跳跃使用其选择的目标集。

### 11.9.1 `remove-opponent-board`

为形成玩家创建一个棋盘义务，对手剩余部分如上所述，目标来自 11.6。对手是下一主动玩家。如果剩余部分将为零，则不为此效果创建磨坊分支。

### 11.9.2 手中棋子

应为 `remove-opponent-hand-change` 和 `remove-opponent-hand-retain`：

1. 为`min(R, opponent hand)`创建手中棋子义务。
2. 如果`R`超过对手的手中棋子，应在棋盘上添加一个行动义务。
应使用目标`~`来计算剩余棋盘上方的剩余部分。
应遵循手中棋子的义务。
3. 忽略零计数义务; 和
4. 应将最终的下一主动玩家设置为对手。`change`应或不得使用特定术语。
形成行动方`retain`。

每次手中棋子减少都表示为移除事件。该事件不在导致事件内部执行。

### 11.9.3 `opponent-remove-own-board`

创建一个板上剩余部分义务，其行为者和目标所有者是对手，剩余部分限制同上，下一主动玩家为对手。如果剩余部分将为零，则不创建此效果的磨坊分支。

### 11.9.4 `mark-opponent-board-until-moving`

构造同样目标分支如 `remove-opponent-board`。

当移除事件应用时，改变选中活跃对手字符为其小写所有者标记。点位变为阻塞状态，活跃材料计数立即减少。

### 11.9.5 延迟执行的当前磨坊数效果

在阶段`p`中，不会立即生成任何磨坊分支。特殊计算仅在11.14中发生于全局落子边界处。

## 11.10 走子阶段的磨坊效果

在阶段 `m`,可用的磨坊创建了形成玩家的棋子移除分支，对抗对手。剩余的被限制为11.9中一样的内容。对手是分支后的下一个主动者。如果剩余的将为零，则不创建磨坊分支。

## 11.11 义务的解决

当一个吃子目标选定分支后：

1. 丢弃未选择的分支;
2. 应用所选棋盘或手中移除效果;
3. 减少 `remaining`;
4. 当事件处于 `resetEvents` 时，重置无进展状态;
5. 在 11.17 中应用即时最小材料测试;
6. 如果剩余值非零，则重新计算该机制的权威目标集；如果它不为空，则保留动作 `r`, 否则应用构造器的零目标回退;
7. 如果义务完成并且在所选分支中另一个义务随后出现，移除已完成项，设置行棋方到下一个项的行动方，具体化其棋盘目标当它们处于 `~` 时，并保留动作 `r` 或应用零目标回退，当目标集非空时;
否则
8. 清空义务，设置行棋方到最终 `after` 玩家，同步阶段与该玩家在 11.12 中，并在步骤 1 复位稳定边界管道。

应进行两次移除的干预，第 6 步只保留配对端点。
对于普通多个磨坊移除，第 6 步重新计算保护措施以适应新棋盘。 没有目标的 `mill-count` 或 `board-full` 的义务被省略，并继续进行确定性处理。 没有目标的 `stalemate` 的义务立即使其行为者失去并且原因是 `no-legal-move`.

应终止游戏的材料测试结束后，所有剩余的义务都会被丢弃，并应用终局状态规则。

## 11.12 主动作序列无义务

当分支构造产生了分支：

- 除非另一个选择的有限效果说保留，否则行棋方会转变为对手；
- 阶段与新行动者同步；
- 早期停止被评估如下；和
- 稳定边界管道继续。

阶段与行动方同步意味着：

- 在全球落子边界之后，阶段是 `m`;
- 在全球落子规则持续期间，持有手中棋子的行动者处于阶段 `p`;
- 在该规则持续期间，持有无手中棋子的行动者即使对手仍有手中棋子也会处于阶段 `m`,
  即使在对手仍有手中棋子的情况下;
- `movementAllowed=true` 还允许在动作为 `p` 时进行移动作为主事件。

应在`after-unobligated-place-v1`后测试早期停止，仅在成功时进行。
应生成的分支不存在。若`emptyPoints`非零且
数量`.`双方手中的点数不超过该点位，双方的手中棋子都归零。
全球落子边界被进入。

它不会在未解决移除之前评估，也不会在该移除完成时回溯性地评估。

## 11.13 全局落子边界和延迟清除

应发生全球落子边界时，两只手中的棋子均为零，或早停设置它们为零。

在界限处：

1. phase变为`m`;
2. 每个延迟的`w`,`b`标记都被更改为`.`;
3. 行棋方从`turn.placingEndActivePlayer`,保留前一个序列选择的玩家;`retain`继续;
4. 确定性处理继续进行，延迟磨坊计数步骤11.20。动作直到管道达到其最后一步才会被最终确定。

清晰的下划线是确定性的，并且不会产生MSTATE事件。

例如在边界上，棋盘片段 `WWW...../b......B/........` 变为
`WWW...../.......B/........`：延迟的黑方标记在后续稳定边界测试前
清为空点，不另生成 remove 事件。

## 11.14 当前磨坊计数移除

应在全球落子边界处，对白色(`Wm`)和黑色(`Bm`)的当前完整活跃磨坊线数进行计数。延迟令牌不参与。

应移除的棋子数量是连续的：

| 条件 | 白方移除 | 黑方移除 | 目标所有权 |
|---|---:|---:|---|
| `Wm=0`, `Bm=0` | 1 | 1 | 每方移除自己的令牌 |
| `Wm>0`, `Bm=0` | 2 | 1 | 对手 |
| `Bm>0`, `Wm=0` | 1 | 2 | 对手 |
| `Wm=Bm>0` | `Wm` | `Bm` | 对手 |
| `Wm>Bm>0` | `Bm+1` | `Bm` | 对手 |
| `Bm>Wm>0` | `Wm` | `Wm+1` | 对手 |

应根据其目标所有者的当前活跃棋子数量限制每个数量，然后省略零计数义务。从剩余的白色义务和剩余的黑色义务中构建一个分支。原因是 `mill-count`. 第一个使用 `after=q` 当第二个存在时。最终的下一位玩家是 `turn.placingEndActivePlayer`, 解决 `retain` 到选定在界限之前的玩家的玩家。后续棋盘义务使用目标 `~` 直到升级。

应在移除对手时应用普通磨坊保护。它不适用于移除自己的标记。如果没有义务生存，继续管道而不暂停。

## 11.15 全盘过渡规则

全盘评估发生在每个持续稳定边界上，无论是在主动阶段还是被动阶段，当义务为空且没有 `.` 的点时发生。它不局限于全球落子边界；这使得总初始材料超过24的清单成为确定性的，而不是让一个阶段 `p` 玩家无法落子。

动作有：

- `disabled`: 无效;
- `first-player-loses`: 黑方获胜，原因是`board-full`;
- `draw`: 和棋，原因是`board-full`;
- `first-then-second-remove`: 一次白方移除黑方的义务，接着一次黑方移除白方的义务，目标是`~`,然后白方行动;
- `second-then-first-remove`: 反向序列，然后黑方行动; 和
- `active-player-removes`: 当前玩家移除一个对手标记，然后对手行动。

应遵循普通的磨坊保护规则。每次请求移除棋子时，最大限度上只会移除当前活跃目标中的一个。零目标状态下的全盘义务将被忽略；如果所有请求的义务都被忽略，则继续进行同时最小材料步骤。在11.11条款下，后续的零目标义务将被忽略。

## 11.16 僵局转换

应在一个稳定的阶段-`m`位置评估僵局。
飞行能力已经被考虑。

当行动方没有合法移动时：

- `loss`: 对手获胜，原因是`no-legal-move`;
- `draw`: 和棋，原因是`no-legal-move`;
- `change-player`: 当前稳定边界评估中，对手最多更换一次，阶段与新行动方同步，管道重启至步骤1；如果僵局步骤在阶段`m`再次触发，并且新的行动方也没有合法移动，则游戏立即结束为和棋，原因是`no-legal-move`;
- `remove-and-retain`: 僵局的玩家移除一个邻近对手活跃棋子，然后继续行动;
- `remove-and-change`: 僵局的玩家移除一个邻近对手活跃棋子，然后对手继续行动; 或
- `both-remove`: 僵局的玩家移除一个邻近对手棋子，然后对手移除一个目标被延迟为`~`,然后僵局的玩家继续行动。

对于这些僵局移除，目标是合法的，当且仅当它是移除者的活棋子之一邻近至少一个活棋子时。磨坊保护不被应用。如果第一个目标集为空，则僵局玩家立即输掉，并且原因为 `no-legal-move`. 如果延迟后僵局义务实现到空目标集，那么该义务的执行者也会输掉，同样是因为这个原因。

对于`change-player`，一旦稳定边界管道在11.20中评估过一次，就不再允许对手更换超过一次。如果同步选择阶段`p`,僵局就不再适用，并且不会为该玩家进行移动测试。

## 11.17 最小材料

每次棋盘或手中棋子移除后，立即计算受影响的所有者：

```text
live board pieces + hand pieces
```

延迟标记已经被移除的材料，排除在外。

如果总数小于 `minimumLive`, 那么该玩家立即输掉，并且原因是 `fewer-than-minimum`. 这个测试适用于落子和移动时。它不等待双方的棋子数量都为零。

如果一个玩家被命令移除自己的一枚棋子，导致其下限少于最小值，那么另一个玩家获胜。

在稳定边界最小材料步骤中，评估两个玩家的相同前一步状态。如果恰好有一个玩家低于 `minimumLive`, 则另一个玩家获胜。如果双方都低于它，则游戏是和棋，并且原因是 `fewer-than-minimum`.

## 11.18 无进展

主事件成功后：

1. 如果其类型在 `countedPrimaryActions`, 则增加无进展计数;
2. 如果主动事件、后续移除事件或检测到的磨坊形成发生在 `resetEvents` 中，则重置为零;
3. 在义务存在期间保留中间值；以及
4. 只有当主序列稳定时才评估。

如果 `endgamePredicate=either-player-live-equals-3`，并且双方都恰好有三个活棋子，则使用 `endgameLimit`, 否则使用 `normalLimit`.

应禁用零限制。若限制大于或等于零：

- `automatic`结束游戏为`d:no-progress`, 或
- `claim`使得有效的`claim-draw`事件生效，但自身不改变MFEN。

## 11.19 重复

重复观察和重置应遵循9.10。

相等应是`legal-state-v1`的每个成员的相等，包括所有声明的语义状态。不得仅仅是棋盘的相等。

若配置的发生次数达到：

- `automatic`结束游戏为`d:repetition`, 或
- `claim`使得有效的`claim-draw`事件生效。

## 11.20 稳定边界和终局优先

应在义务队列变空或主动作创建无义务时，使用此顺序进行确定性处理，并在第一个终局结果处停止：

1. 进入全局落子边界并清除延迟令牌，按时执行；
2. 生成延迟磨坊计数义务，按时执行；
3. 评估整个棋盘；
4. 同时评估双方的最小物质；
5. 评估僵局，携带一致性守卫在任何管道重启中，如11.16所述；
6. 进行重复观察和自动重复裁决；
7. 评估自动无进展；并
8. 在结果阶段仍在进行时设置动作。

如果步骤2、3或5创建一个非空义务队列，行棋方应等同于每个分支头行动方，动作应变为`r`,管道应立即暂停。它只在选定的分支为空时才恢复，并重新启动步骤1。11.14至11.16中的构造器特定零目标规则在队列暴露之前应用。

11.17中立即移除最小测试发生在此稳定边界列表之后。僵局优先于重复，因此观察描述了每个确定性行棋方变化后的最后非终局稳定状态。

一个MSTATE重放器应在义务字段为`-`的每个进行中的起源上运行此管道，经过起源验证和种子领先`pre-origin`重复历史和`preOriginClaims`, 在应用事件之前。管道内的重复观察仍然取决于清单的观察规则。

此顺序连同 11.3 的触发顺序和 11.8 的分支承诺，是
`mif-finite-rules-v2` 的政策及其规则语义的一部分。MRS 选择适用该
政策的机制，不编码优先级列表。实现若声称使用此语义配置文件和同一
清单摘要，就不得选择不同优先级；其他语义配置文件可以规定另一顺序，
但该顺序不是通用 MIF 政策。

## 11.21 终局标准化

一个终局转换应：

- 应设置阶段 `o`;
- 应设置动作 `o`;
- 应设置方 `-`;
- 应设置义务 `-`;
- 保留棋盘、手中棋子、计数器和语义扩展作为事件后的状态;
  和
- 应从附录B中选择一个终局结果原因。

## 12.4 转换状态契约

符合性的 `MIF 转换器` 对每次请求的转换应恰好报告表 7 中的一种状态。

**表 7 — 转换状态**

| 状态 | 含义 |
|---|---|
| `lossless` | 目标语义所需的全部权威源值均得到保留 |
| `lossy-history` | 瞬时游戏状态保留，但事件、重复、声明、提议或来源历史被省略 |
| `lossy-semantic-state` | 目标无法保留已知的、依赖序列的游戏语义状态 |
| `requires-ruleset-resolution` | 必须先解析完整、带版本的规则集上下文才能判断可表示性 |
| `unrepresentable-under-profile` | 所选目标格式或配置文件无法表示所需的已知状态 |

报告外壳和 API 由实现定义。状态名和下列行为是规范性的；本版不新增
大型线格式。

转换器应按以下顺序选择状态：

1. 所需规则集身份或语义尚未解析时为
   `requires-ruleset-resolution`；
2. 已解析目标无法编码所需已知状态时为
   `unrepresentable-under-profile`；
3. 只有省略已知序列依赖游戏状态才能产生有用目标时为
   `lossy-semantic-state`；
4. 仅省略非瞬时历史时为 `lossy-history`；否则
5. 为 `lossless`。

对于 `requires-ruleset-resolution` 和
`unrepresentable-under-profile`，转换器不得输出貌似有效的目标记录。
对于两种有损状态，转换器应指出省略的信息，并且只有调用方明确接受后
才能输出目标。修复、猜测或默认补全的状态不得标为 `lossless`。

规范转换向量覆盖 NMM_LLM 原子移动加吃子、Sanmill 无所有者 `X`、
缺失的 `ul` 历史以及缺失的规则集上下文。

# 13 规范化、版本控制、扩展和注册

## 13.1 规范等值性

MFEN 文本规范等值性是其 US-ASCII 记录的字节等值。由于 MFEN 不自描述，语义位置等值还需要相同的调用方提供规则集 ID 和版本。

MPK 规范等值性是其 US-ASCII 记录的字节等值；MPK 带有其规则集 ID 和版本。

规范 MSTATE 和 MRS 等值性是其 RFC 8785 JCS UTF-8 八位字节的字节等值，所有语义数组顺序要求都已执行后。

JCS 单独不规范化表示为数组的集合。第 9 条和表 6 在应用前应适用。

## 13.2 草案格式版本

本版签名是：

```text
MFEN/0.4
MPK/0.4
MSTATE/0.4
MRS/0.4
```

他们故意不是之前提出的 `MFEN/2`、`MPK/1`、
`MSTATE/2` 或 `MRS/1`,没有稳定的版本是由此工作草案冻结的。

生产者应只发射它实现的签名。消费者不得将未知的签名解释为最近的已知版本。

本版使用一个封闭的词汇配置文件。附录C的ABNF枚举了标准结果原因、标准扩展键和义务原因。
添加一个新的非 `x-` 标准令牌需要升级格式或状态配置文件。仅靠注册表条目不能扩展这些封闭的枚举。
私有 `x-`标识符仍然是实验路径。

将MRS摘要分解为游戏 `semanticDigest` 和完整文档 `documentDigest` 的问题延迟到本版之后。

## 13.3 规则集更改

规则集版本应在游戏行为可以改变时发生变化，包括法律动作、触发优先级、目标、回合控制、和局终结结果。

规则集版本不必仅因为：

- 另一个状态配置文件可以编码相同的权威状态；
- 选择了另一个MPK键配置文件；
- 数据库更改二进制打包；或
- 无法改变规范化清单的可信息元数据。

应因为规范化的清单包含了本版的标题和状态，出版商想要改变这些成员而不改变游戏规则版本时，应发布注册注释，而不是变更清单字节。

## 13.4 私有扩展

私有标识符应开始于`x-`。

未知的私有对象成员和MFEN扩展，若明确非语义，可保留并回转。它们不得改变法律行为、重放、终局结果或键。它们不得出现在MPK中。

一个由外部配置文件声明为语义的私有扩展，在不实现该配置文件的消费者中应被拒绝。它不得被忽略。

未知的非前缀成员、扩展键和事件类型应被拒绝。

## 13.5 注册政策

一个公共规则集注册宜要求：

a) 一个规范的清单和摘要。

b) 文档化规则来源和治理。

c) 每个非默认转换的明确示例。

d) 应至少有两个独立的实现，或者一个完整的实现
规范性文本等待第二次实现。

e) 跨实现重放协议同意

f) 结束重复，进展不动和终局语义；以及

g) 无未解决的线路或键配置文件问题。

实验或测试应使用`x-`，直到这些条件得到满足。

项目 (b) 中的来源应标识规则来源或规则权威，以及来源版本、日期或版次。
“German（德国）”“Hungarian（匈牙利）”或“English（英国）”等裸标签
不能注册为权威规则集身份，因为它们不指向一套固定的全球规则。只有在
同时限定实际权威和版本时，这些词才可出现在标题中。

应注册状态配置文件和键配置文件，独立于规则集。

## 13.6 媒体类型

本工作草案未注册任何媒体类型。

未来工作可能评估以下名称：

```text
application/mill-state+json
application/mill-ruleset+json
application/mill-position
application/mill-position-key
```

应遵循RFC6838和更新的RFC9694中的BCP 13进行注册。 JSON表示可以使用RFC6839定义的`+json`结构化语法后缀。

## ABNF

以下语法根据 RFC 5234 和 RFC 7405 进行解释。所有引用的文字都是大小写敏感的。它是一个关闭的词汇配置文件，如第 13.2 节所定义。MPK `key-extension` 允许私有标识符语法上；第 8 条禁止在符合 MPK 输出中非语义的私有扩展。

```abnf
mfen = mfen-signature SP state-profile SP board SP side
       SP phase SP action SP hands SP obligations SP no-progress
       SP primary-ply SP outcome *(SP extension)

mfen-signature = %s"MFEN/0.4"

mpk = mpk-signature SP state-profile SP ruleset SP key-profile
      SP mpk-board SP player SP active-phase SP hands
      *(SP key-extension)

mpk-signature = %s"MPK/0.4"

state-profile = identifier
key-profile = identifier
ruleset = identifier %s"@" positive-integer

identifier = id-start *62id-character
id-start = lc-alpha / DIGIT
id-character = lc-alpha / DIGIT / %s"." / %s"-"
private-identifier = %s"x-" id-start *60id-character

board = ring %s"/" ring %s"/" ring
ring = 8piece
mpk-board = 24piece
piece = %s"W" / %s"B" / %s"." / %s"w" / %s"b"

side = player / %s"-"
player = %s"w" / %s"b"
phase = active-phase / %s"o"
active-phase = %s"p" / %s"m"
action = %s"p" / %s"m" / %s"r" / %s"o"

hands = uint %s"," uint
no-progress = uint
primary-ply = uint

obligations = %s"-" / obligation-branches
obligation-branches = obligation-branch *(%s"|" obligation-branch)
obligation-branch = obligation *(%s";" obligation)
obligation = player %s":" cause %s":" target-zone %s":" player
             %s":" positive-integer %s":" target-spec %s":" after

cause = %s"leap" / %s"intervention" / %s"custodian" /
        %s"mill" / %s"mill-count" / %s"stalemate" /
        %s"board-full"
target-zone = %s"b" / %s"h"
target-spec = hex24 / %s"-" / %s"~"
after = player / %s"q"

outcome = %s"-" / result %s":" reason
result = %s"w" / %s"b" / %s"d"
reason = standard-reason / private-identifier
standard-reason = %s"fewer-than-minimum" / %s"no-legal-move" /
                  %s"board-full" / %s"no-progress" /
                  %s"repetition" / %s"agreement" /
                  %s"resignation" / %s"adjudication"

extension = extension-key %s"=" *value-character
key-extension = extension
extension-key = standard-extension-key / private-identifier
standard-extension-key = %s"lm" / %s"pc" / %s"ul"
value-character = %x21-3C / %x3E-7E

; Registered extension-value subgrammars.
lm-value = coord-or-dash %s"," coord-or-dash %s";"
           coord-or-dash %s"," coord-or-dash
pc-value = uint %s"," uint
ul-value = line-bitset %s"," line-bitset
line-bitset = 4lc-hex / 5lc-hex

hex24 = 6lc-hex
coord-or-dash = coord / %s"-"
coord = %s"a7" / %s"d7" / %s"g7" / %s"g4" /
        %s"g1" / %s"d1" / %s"a1" / %s"a4" /
        %s"b6" / %s"d6" / %s"f6" / %s"f4" /
        %s"f2" / %s"d2" / %s"b2" / %s"b4" /
        %s"c5" / %s"d5" / %s"e5" / %s"e4" /
        %s"e3" / %s"d3" / %s"c3" / %s"c4"

uint = %s"0" / positive-integer
positive-integer = nonzero-digit *DIGIT
nonzero-digit = %x31-39
lc-hex = DIGIT / %x61-66
lc-alpha = %x61-7A
```

独立的 `conformance/mif-0.4.abnf` 文件是机器可读的副本。如果出版缺陷导致这两个副本不同，工作组应在推进草稿之前纠正两者；任何差异都不得被实现选择忽略。

`lossy-semantic-state` 并在输出简化结果前取得调用方明确接受；它不得
猜测哪一条线产生了相同的点联合。

已检查的首选移除值是应用提示，用于在应用创建干预上下文的主动时。它不是本版的持久法律状态。一个转换器应解析指示的原始候选线，并且当该线非默认时，在MSTATE `place` 或 `move` 事件上发射其表A.2 ID作为 `interventionLine` 。一旦有一个等待的MFEN被产生，发布的义务分支直接携带所需的上下文。

`ids:nodes` 标记没有MIF等价。坐标和公共位顺序由附录A固定。

应为 Mill 游戏，棋子数量和行动方的变化可能无法重建主动步数。

### E.4 内部布局和性能

没有需要采用表 A.1 作为其搜索布局的实现被检查过。

导入和导出可以使用固定 24 个条目排列。转换发生在文本、API 或数据库边界处一次。移动生成、评估、Zobrist 更新和递归搜索可以继续使用原生位的位置。

在这种架构下：

- 文字环顺序不会增加到搜索热路径中的工作量;
- 原生的位操作保持不变;
- MPK 正规化可以在复制 24 个单元投影上运行; 和
- 数据库可能将规范结果打包到其自己的二进制键中。

# 附录 F (非正式)

## 设计决策和草案推进

### F.1 保留的架构

三个表示法保持分开，因为它们回答不同的问题：

| 表示法 | 问题 |
|---|---|
| MFEN | 现在存在哪些准确规则？ |
| MPK | 稳定状态使用哪个结构分析桶？ |
| MSTATE | 这个游戏、历史和声明如何恢复和审计？ |

MRS 描述了行动如何改变状态；它不是第四种位置格式。

### F.2 社区工作草案 0.1 的破坏性变化

0.2 版本：

- 将实验性签名更改为 `0.2`;
- 移除 `ready` 阶段；
- 分离状态配置文件、规则集和键配置文件；
- 替换待处理计数和全局标志为类型化的义务分支；

- 定义标记延迟作为移除效果，并将其视为确定性的；
- 替换形成点历史记录为每行规则一次使用的玩家线位集；

- 采用 I-JSON 和精确数组规范化；

### F.5 为什么保留 `phase` 和 `action`

阶段描述了规则的范式; 行动描述了下一个输入。 最终的落子可以将阶段设置为 `p`，手中棋子为零，并且行动为 `r`. 不对称的手中棋子移除也可以使一名玩家移动，而另一名玩家仍在落子。 移除任何一个字段都会使一些中间状态模糊或强制隐含推理。

### F.6 为什么 `hand` 是直接值

应提供当前可用的令牌数量。计数历史和可以从手中移除后分叉的材料。直接手是核心，因此可选`pc`是单独的。

### F.7 为什么在 MFEN 中保留义务

用户可以在捕获选择期间暂停。分析或 UI 工具也需要检查该exact 选择。将其转换为稳定局面会改变法律状态，并且不是无损的。

### F.8 为什么存在两个结构键配置文件

D4 匹配视觉板对称性和部署 NMM_LLM 正规化。外部/内部交换是额外的拓扑自同构。两者都有用；两者都不应隐藏在规则集版本中，也不应在现有数据库中静默替换。

### F.9 稳定候选条件之前的条件

工作组不应在以下情况下冻结稳定的签名：

- 两种独立的实现重放集合时相同;
- 至少有两个非平凡的清单通过跨语言重放;
- 每个变换和语义扩展都有逆坐标测试;
- 自动和声称的平局周期具有长形式向量;
- legacy 转换报告具有明确的损失类别;
- 解析器模糊覆盖 ABNF、重复 JSON 名称和资源限制; 和
- 规则集/配置文件注册管理有达成一致。
